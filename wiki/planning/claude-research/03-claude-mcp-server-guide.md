# MCP memory servers for Claude Code: a power user's guide

**The MCP memory ecosystem has exploded in early 2026, offering at least a dozen viable persistent memory servers — but for a power user with git-tracked session archives, the real question is not which server to adopt, but which architecture complements your existing workflow.** The landscape spans five architectural approaches: simple knowledge graphs (the official reference server), auto-extracting two-tier systems (memory-mcp), hybrid SQLite-plus-vector engines (doobidoo's mcp-memory-service), cloud-backed vector stores (Mem0/OpenMemory), and Markdown-native systems (Basic Memory). Each makes fundamentally different tradeoffs between setup complexity, token costs, search quality, and human inspectability. For someone already running structured session archives with metadata tagging, the strongest path is likely a hybrid: keep your git archives as the canonical record while layering an MCP server for real-time mid-session retrieval and automatic extraction.

## The five contenders worth evaluating

The field is crowded, but five servers represent distinct architectural categories that matter for decision-making.

**@modelcontextprotocol/server-memory** is the official Anthropic reference implementation, part of the 74,500-star MCP servers monorepo. It implements a local knowledge graph with three primitives — entities, relations, and observations — stored in a **JSONL file**. Version `2025.11.25` gets roughly **28,000 weekly npm downloads**. It exposes 9 tools (create/delete entities, relations, observations, plus `search_nodes`, `open_nodes`, and `read_graph`). Search is pure substring matching — no vectors, no semantics, no AI processing whatsoever. Claude itself decides what to store and when. Setup is a single command: `npx -y @modelcontextprotocol/server-memory`. The JSONL format is human-readable, git-trackable, and manually editable. The tradeoff: it's deliberately minimal. No timestamps on memories, no expiration, no consolidation, no hooks integration. It loads the entire graph into memory on each operation, so it won't scale to tens of thousands of entries.

**memory-mcp by yuvalsuede** launched in late January 2026 and takes a radically different approach. It auto-generates a compact **CLAUDE.md briefing** (Tier 1, ~150 lines) from a full `.memory/state.json` store (Tier 2, unlimited). Claude Code natively reads CLAUDE.md on session start, giving the system zero-cost context injection for 80% of sessions. The remaining 20% pull from Tier 2 via MCP tools including `memory_search`, `memory_ask` (Haiku-synthesized answers from top 30 matches), and `memory_related`. Auto-extraction fires via Claude Code hooks on Stop, PreCompact, and SessionEnd events, sending transcript chunks to **Claude Haiku at ~$0.001 per extraction**. A full day of active development costs roughly **$0.05–$0.10**. It categorizes memories into six types (architecture, decision, pattern, gotcha, progress, context) with confidence decay — progress memories have a 7-day half-life, while architecture and decisions never decay. Deduplication uses Jaccard similarity at 60% threshold plus LLM consolidation every 10 extractions. The catch: it's very new (10 commits, 0 stars) and untested by the community.

**doobidoo/mcp-memory-service** is the most feature-rich option with **852 stars and 1,419 commits**. It combines SQLite with sqlite-vec for ONNX-based embeddings, delivering **5ms semantic search** without external API dependencies. Features include a dream-inspired memory consolidation system (decay scoring, association discovery, compression), a web dashboard with 8 tabs at localhost:8000, D3.js knowledge graph visualization, graph traversal tools (`find_connected_memories`, `find_shortest_path`), and Claude Code hooks for auto-capture. It supports 13+ AI clients. The model requires **400–600 MB RAM** for the sentence transformer. However, its changelog reveals significant stability history — version 10.0.0 shipped with broken tool loading, and multiple critical hotfixes addressed SQLite bugs and semantic search failures. Now at v10.4.4, it's more stable but carries meaningful operational complexity.

**Mem0/OpenMemory** brings a commercial-grade approach with Qdrant vector search plus Postgres metadata. The OpenMemory variant runs entirely locally via Docker Compose with a web dashboard for memory auditing and cross-client sharing (Cursor, Claude, VS Code, Windsurf). It requires an **OpenAI API key for embeddings**. The cloud-hosted `mem0-mcp` option uses a Mem0 API key instead. Both offer semantic search that dramatically outperforms substring matching. The tradeoff is setup complexity (Docker + Qdrant + Postgres) and the external embedding dependency.

**Basic Memory** stores everything as standard **Markdown files** with a SQLite index for search. It integrates directly with Obsidian, supports `memory://` URIs for context navigation, and requires zero external APIs. For someone already comfortable with Markdown and git, this is the most philosophically aligned option — your memory is just files you can read, edit, grep, and version-control. The downside is that search quality depends on keyword matching rather than semantic understanding.

## Architecture decisions that actually matter

The choice between these servers hinges on three architectural axes: how memories get in, how they get out, and what they cost.

**Extraction method** divides the field into two camps. The official server-memory and Basic Memory are purely manual — Claude decides what to store via explicit tool calls during conversation. memory-mcp, doobidoo, and claude-recall use **Claude Code hooks** for automatic extraction, firing on lifecycle events (SessionEnd, Stop, PreCompact). Hook-based extraction means memories accumulate without you asking, but it introduces token costs. memory-mcp routes through Haiku at $0.001/extraction. doobidoo uses local ONNX embeddings (free but resource-intensive). The official server uses no AI processing at all — zero incremental cost.

**Retrieval quality** varies enormously. The official server uses case-insensitive substring matching — searching "authentication" won't find memories about "JWT tokens" or "login flow." memory-mcp adds Haiku-synthesized answers via `memory_ask`, meaning you can ask natural-language questions and get a synthesized response from the top 30 matching memories. doobidoo and Qdrant MCP offer true **semantic vector search**, finding conceptually related memories even without keyword overlap. For a power user accustomed to precise `grep` queries, substring matching may feel familiar but limiting; vector search finds things you didn't know to search for.

**Storage and inspectability** is where your existing git workflow becomes relevant. The official server's JSONL, memory-mcp's JSON, and Basic Memory's Markdown are all **plaintext, git-diffable, and human-editable**. doobidoo's SQLite is inspectable via standard tools but not git-diff-friendly. Mem0's Qdrant+Postgres stack is essentially opaque without dedicated tooling. For someone who values git-tracked everything, plaintext formats have a clear advantage. memory-mcp goes further: its CLAUDE.md output lives in your repo's root, meaning memory summaries automatically appear in your git history.

**Scoping** defaults to per-project for most servers. The official server achieves this via `MEMORY_FILE_PATH` environment variables — point different projects at different JSONL files. memory-mcp stores `.memory/state.json` per project directory. Cross-project sharing requires pointing multiple projects at the same file or building a custom aggregation layer. No server handles multi-project knowledge sharing elegantly out of the box, though mcp-knowledge-graph and xgmem have made early attempts with named databases and `projectId` parameters.

## Migrating from git archives without losing your investment

Your existing workflow — session archives tracked in git with metadata tagging and search/retrieval prompts — represents significant accumulated value. The good news: **MCP memory servers coexist peacefully with git-tracked archives**. They operate in completely separate channels — your Markdown files stay on disk, the MCP server runs as a sidecar process communicating over stdio.

The migration path that preserves the most value is incremental. Keep your archives as the canonical long-term record. Add an MCP server for real-time retrieval during sessions. Over time, the MCP server handles the "what did we decide about X?" questions that currently require you to grep through files.

**Seeding an MCP server with existing context** is straightforward for plaintext formats. The official server's JSONL accepts entities like `{"type":"entity","name":"Auth_Module","entityType":"architecture","observations":["Uses JWT with RS256","Tokens expire after 24h"]}`. A simple script can parse your session archives, extract key facts, and write them as JSONL entities with relations. memory-mcp's state.json is similarly scriptable — each memory entry has type, content, confidence, tags, and timestamps. Basic Memory accepts Markdown files directly, making it the lowest-friction import target.

For preserving your existing tagging system, knowledge graph servers map naturally. Your tags become entity types or observation metadata. The official server's free-form `entityType` field accepts any string, so your existing taxonomy transfers directly. memory-mcp's six fixed categories (architecture, decision, pattern, gotcha, progress, context) are more opinionated — you'd need to map your tags into these buckets or accept some information loss.

**memory-mcp's CLAUDE.md approach deserves special attention** for migration. It inserts its generated content between `<!-- MEMORY:START -->` and `<!-- MEMORY:END -->` markers, preserving everything else in your CLAUDE.md. If you already maintain a CLAUDE.md with project context, the two systems coexist without conflict. Your handwritten context stays above or below the markers; the auto-generated memory summary lives between them.

## What power users actually need from memory curation

Mid-session search, manual editing, and export capabilities separate tools built for power users from those built for demos.

**Searchable memory mid-session** is supported by all major servers, but with different capabilities. The official server's `search_nodes` does substring matching across entity names, types, and observations. memory-mcp offers three retrieval modes: `memory_search` (keyword), `memory_related` (tag-based), and `memory_ask` (Haiku synthesizes an answer from matching memories — the most powerful option for natural-language queries). doobidoo provides true semantic search at 5ms latency.

**Memory editing and curation** is where the official server excels through simplicity. Its `delete_entities`, `delete_observations`, and `delete_relations` tools give fine-grained control. You can also directly edit the JSONL file in any text editor. memory-mcp offers `memory_delete` and `memory_consolidate` (LLM-powered merge/prune), plus manual state.json editing. doobidoo provides a web dashboard for visual memory management. No server currently offers a dedicated `memory_edit` tool for in-place modification of individual entries — you either delete and recreate, or edit the backing file directly.

**Export and backup** strategies depend on storage format. JSONL and JSON formats are inherently exportable — copy the file. Git-track it for versioned backup. memory-mcp adds git snapshots on a hidden `__memory-snapshots` branch, providing automatic versioning tied to work sessions with diff and restore capabilities. SQLite-based servers require standard database backup approaches. For your use case, plaintext formats that slot into your existing git workflow are clearly preferable.

**Multi-project knowledge sharing** remains the weakest area across the ecosystem. The practical workaround is maintaining a global memory file alongside per-project files. Configure the MCP server at user scope (`claude mcp add memory --scope user`) for cross-cutting knowledge (personal preferences, common patterns) and project scope for project-specific context.

## The custom server question and hybrid architectures

Building a custom MCP memory server is **surprisingly approachable** with the official TypeScript SDK (`@modelcontextprotocol/sdk`). A minimal server that wraps your existing git-tracked archives with `store_memory` and `search_memory` tools requires roughly 50–100 lines of TypeScript. The SDK handles protocol compliance, JSON-RPC transport, and type safety. Testing uses `npx @modelcontextprotocol/inspector`. Registration is one command: `claude mcp add --transport stdio my-server -- node /path/to/server.js`.

For someone with your existing infrastructure, a custom server could search across your session archives, respect your metadata tags, and write new memories in your established format — something no off-the-shelf server will do. The investment is a few hours of development versus adapting your workflow to someone else's data model. The Python SDK (`mcp[cli]`) is equally viable and may integrate more naturally with text processing pipelines.

**The strongest hybrid architecture for your situation** combines three layers. First, keep your git-tracked session archives as the permanent record — they're battle-tested and you control the format. Second, add the official `@modelcontextprotocol/server-memory` for lightweight, zero-cost knowledge graph persistence that Claude can query mid-session. Third, consider memory-mcp's hook-based auto-extraction to capture session learnings without manual intervention, feeding into an auto-generated CLAUDE.md for next-session context. The three layers serve different timescales: hooks capture the present, the knowledge graph serves the current session, and git archives preserve history.

An alternative hybrid uses Basic Memory as the MCP layer, since its Markdown storage is philosophically identical to your archive system. You'd gain MCP-accessible search without changing your mental model of "memory is files."

## Conclusion

The MCP memory ecosystem in early 2026 offers genuine capability but no single dominant solution. **The official server-memory is the safest starting point** — it's actively maintained, trivially installed, uses an inspectable JSONL format, and imposes zero token costs. It's limited by substring-only search and lack of auto-extraction, but it establishes the baseline. **doobidoo's mcp-memory-service is the most capable** option with semantic search, auto-capture hooks, and visualization, but carries meaningful operational complexity and a bumpy stability history. **memory-mcp is the most architecturally interesting** for its two-tier CLAUDE.md approach, though it's too new to recommend for production use.

For a power user with your infrastructure, the highest-leverage move is not adopting any single server wholesale — it's adding the official server for mid-session retrieval (5-minute setup, zero ongoing cost), keeping your git archives as ground truth, and evaluating whether hook-based auto-extraction (via memory-mcp or doobidoo) adds enough value to justify the Haiku token spend of roughly $2–3 per month. If none of the off-the-shelf options fit your metadata model, building a custom server wrapping your existing archives is a realistic weekend project with the TypeScript or Python SDK.
