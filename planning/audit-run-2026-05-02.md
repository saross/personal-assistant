# Audit Run Execution Plan — 2026-05-02

## 1. What `/audit` actually does

Read from `/home/shawn/personal-assistant/commands/audit.md`. Key facts that drive the rest of the plan:

- **Read-only.** The skill performs analysis only; it does not modify files.
- **Per-file granular line-by-line audit.** Each file gets a full pass against six categories: logic errors, data-format assumptions, edge cases, cross-module consistency, security, project conventions (incl. UK/AU English).
- **Built-in fan-out.** Section 2 of the skill says: *"Use subagents to audit files in parallel when there are 2+ files. Each subagent receives the full audit prompt below."* Parallelism is native — we are not bolting it on.
- **Built-in cross-file analysis pass** (section 3) — runs after individual file audits.
- **Built-in self-review loop** (section 5) — the audit re-reads its own findings to strip false positives and re-scans for missed bugs.
- **Output schema is fixed** — Critical / Medium / Low / Cross-file issues / No issues found, with File:line, Category, Description, Impact for each finding.
- **Has a `--scope project` flag** — would in principle do the whole job in one invocation. We will deliberately *not* use it (see section 2 below).

The skill expects File:line precision and full-line scrutiny — not a sweeping summary. That dictates how we partition.

## 2. Parallelism decision: **Multi-agent fan-out, with a synthesis pass**

Reasoning, not just verdict:

1. **Real LOC is 13,032, not 12,720.** The prompt's inventory missed `bulk-archive.py` (1,249), `tag-gardening.py` (778), and `zotero.py` (662). A single agent would need to ingest >13K LOC plus the audit prompt itself plus produce a structured report — context-window strain is real. Even at 1M context the *quality* degrades on a granular line-by-line task as the file count grows; attention dilutes.
2. **The skill mandates per-file granularity.** "Line-by-line, presuppose bugs exist." That is fundamentally per-file work. There is no synthesis advantage to having one agent read all files at once — the per-file audits are independent.
3. **The skill itself prescribes subagent fan-out for 2+ files.** Following the skill literally on `--scope project` would already trigger fan-out internally; we are simply choosing the fan-out *boundaries* deliberately rather than letting the skill auto-partition 26 files into 26 subagents (which would lose cross-file context and burn tokens on duplicated setup).
4. **Cross-file consistency is real but bounded.** It only matters within clusters that actually share state (memory pipeline, postgres cluster, daily-sync chain). External integrations and glue scripts have minimal cross-coupling. So we cluster by *coupling*, not by file count.
5. **Calibration risk.** A single agent producing one giant report tends to compress severity — everything looks medium when there are 200 findings. Partitioned reports preserve per-cluster severity granularity which the synthesis pass can then re-tier.

**Verdict: hybrid multi-agent fan-out — one subagent per cluster (5 clusters), then one synthesis agent.** Not one-agent-per-file (too much overhead, weak cross-file analysis within cluster), not one-agent-total (context strain, severity flattening).

## 4. Execution order

All five cluster audits **fire in parallel as the first wave** — they share no context and have no inter-cluster dependencies. Each is independent.

**Wave 1 (parallel, 5 agents):** Cluster A, B, C, D, E. Each agent receives:
- The full `/audit` skill prompt (from `commands/audit.md`).
- An explicit file list (only the files in its cluster).
- Instruction: "Produce the standard audit report for these files only. Include an inter-file consistency section *within this cluster*. Do NOT speculate about files outside the list."
- Output destination: `~/personal-assistant/reports/audit-2026-05-02/cluster-{A,B,C,D,E}.md`.

**Wave 2 (sequential, 1 agent — synthesis):** After all 5 cluster reports exist, a synthesis agent runs with this brief:
- Read all 5 cluster reports.
- Re-tier severities for consistency (cluster A's "medium" should match cluster D's "medium").
- Identify **inter-cluster** consistency issues — e.g. does `extraction-hook.py` (cluster A) write a data structure that `sync-to-postgres.py` (cluster B) reads? Are the schemas aligned? This is the cross-file check that no individual cluster could perform.
- Produce a top-level executive summary (count of critical/medium/low, top 10 most urgent items, suggested fix order).
- Output: `~/personal-assistant/reports/audit-2026-05-02/SUMMARY.md`.

**Wave 3 (optional, sequential, 1 agent — verifier):** For every Critical-tier finding flagged in any cluster report, a verifier agent re-reads the *live source* at the cited File:line and confirms the bug is real (not a false positive caused by missing context). Output: appended verification status to `SUMMARY.md` (CONFIRMED / FALSE-POSITIVE / NEEDS-HUMAN). This addresses the skill's section 5 self-review at the orchestration level rather than relying solely on each subagent's internal loop.

## 5. Output format

```
~/personal-assistant/reports/audit-2026-05-02/
├── SUMMARY.md                       <- executive summary, re-tiered, verified
├── cluster-A-memory-pipeline.md
├── cluster-B-postgres.md
├── cluster-C-hooks.md
├── cluster-D-integrations.md
└── cluster-E-glue.md
```

Each cluster report follows the `/audit` skill's prescribed schema (Critical / Medium / Low / Cross-file / No issues found, with File:line + Category + Description + Impact per finding).

`SUMMARY.md` adds three sections beyond the skill's schema:
- **Top-of-list action items** — the 10 most urgent findings across all clusters, ordered by severity then by blast radius.
- **Inter-cluster consistency findings** — anything that crosses cluster boundaries.
- **Verification status table** — for every Critical, the verifier's CONFIRMED / FALSE-POSITIVE / NEEDS-HUMAN flag.

Date stamp `2026-05-02` is in the directory name (per requested filename convention) so multiple audit passes can coexist over time.

## 6. Cost / time estimate

**Multi-agent (the chosen plan):**
- Wave 1: 5 parallel agents, each handling 1–5K LOC. The largest (Cluster A at ~5K LOC) sets the wall-clock floor. Per-agent runtime estimate: 4–8 minutes for granular line-by-line + self-review loop. Wall-clock: ~8 min.
- Wave 2 (synthesis): reads ~5 reports of perhaps 2–5K tokens each, produces synthesis. ~2–3 min.
- Wave 3 (verifier, optional): depends on # of Critical findings. Estimate 10–30 critical findings, ~30 sec each to re-verify against source. ~5–15 min.
- **Total wall-clock: ~15–25 minutes.**
- **Token cost (Sonnet/Opus tier):** input ~13K LOC ≈ 130K tokens read once per cluster + skill prompts ≈ 200K input across all agents. Output ~30K tokens of reports. Order-of-magnitude estimate: **$5–15 USD on Opus-tier, $1–3 on Sonnet-tier.**

**Single-agent comparison:**
- Wall-clock: 30–60 min serial reading + analysis.
- Token cost: similar input total but quality-degraded, so likely re-runs needed. Net cost equal or higher.
- Quality hit is the dominant factor, not cost.

**Multi-agent wins on time and quality, ties on cost.**

## 7. Risks and safeguards

| Risk | Safeguard |
|---|---|
| Agent invents a bug that does not exist (hallucinated File:line) | Wave 3 verifier re-reads live source for every Critical finding before it lands in `SUMMARY.md`. |
| Agent misses a cross-cluster bug (e.g. memory pipeline writes a field that postgres sync misreads) | Wave 2 synthesis agent's *only job* is inter-cluster consistency checks. Brief it explicitly with: "your distinguishing value is finding bugs that no single cluster agent could see." |
| Agent flags style nits as Critical, drowning real issues | Synthesis agent re-tiers using the skill's severity definitions (Critical = crashes/data loss/wrong results only). |
| `_bulk_rewrite_guard.py` contract breaks across its 4 callers | All 4 callers + the guard itself are in Cluster A — same agent context. |
| `schema.sql` drift vs Python writers | Schema and all writers in Cluster B — same agent context. |
| Agent doesn't know project conventions (UK/AU English, CLAUDE.md rules) | Each cluster agent must be given `~/personal-assistant/CLAUDE.md` plus the conversion table reference *before* starting. The skill mentions this but the agent will skip it unless the orchestrator preloads it. |
| Daily-sync re-audit produces nothing new because Shawn just fixed it | Excluded from main run; offered as optional standalone calibration pass per section 3. |
| 1,249-LOC `bulk-archive.py` skews Cluster E's wall-clock | Acceptable — Cluster E still finishes well before Cluster A. |
| Findings get lost or overwritten between waves | Each wave writes to a distinct file path; synthesis reads, never overwrites. |
| Run interrupted mid-wave-1 | Each cluster report is self-contained; failed clusters can be re-run individually without re-running the whole thing. |

## 8. What this plan does NOT do

- Does not run `/audit`. Orchestrator dispatches.
- Does not modify any source code. The audit itself is read-only by skill design; any fixes are out of scope.
- Does not produce findings. The plan produces an *execution recipe*; the agents produce findings.
- Does not include `tests/`, `agents/`, `archive/`, `data/`, `docs/`, `published/`, `venv/`, the `.md` libraries, or `settings.json`. Operational scripts only, as Shawn requested.
- Does not include the daily-sync cluster (rationale in section 3); offered as optional standalone follow-up.
